# Архитектура

Статус: **действует**. Любое изменение границ крейтов — через ADR.

## 1. Контекст

```
        ┌──────────────────────────────┐
        │            UI (Slint)        │  пользователь, без админа
        └──────────────┬───────────────┘
                       │ IPC (named pipe, ACL текущего пользователя)
        ┌──────────────▼───────────────┐
        │        vpn-service           │  Windows-служба, SYSTEM
        │  ┌────────────────────────┐  │
        │  │ vpn-core (сессия)      │  │
        │  │ vpn-tun  (wintun)      │  │
        │  │ vpn-dns  (fake-IP)     │  │
        │  │ vpn-routing (правила)  │  │
        │  │ vpn-proto (outbound)   │  │
        │  └────────────────────────┘  │
        └──────────────┬───────────────┘
                       │ TCP/UDP через выбранный протокол
                 ┌─────▼─────┐
                 │  сервер   │
                 └───────────┘
```

## 2. Процессная модель

| Процесс | Права | Ответственность | Запрещено |
|---|---|---|---|
| `vpn-desktop` | обычный пользователь | UI, настройки, импорт профилей | открывать TUN, менять маршруты, работать с секретами службы |
| `vpn-service` | SYSTEM | TUN, DNS, маршруты, протоколы, kill switch | рисовать UI, читать пользовательские файлы без запроса |

Правила:

- UI **никогда** не выполняется с повышенными правами.
- Служба **никогда** не принимает команды от процесса с другой integrity level.
- IPC-сообщения валидируются на стороне службы (не доверяем UI).
- Секреты (ключи, пароли профилей) хранятся в защищённом хранилище службы,
  UI получает только маскированные значения.

## 3. Крейты и правила зависимостей

```
vpn-config   ← vpn-proto, vpn-core, vpn-ipc
vpn-routing  ← vpn-core, vpn-service
vpn-dns      ← vpn-core, vpn-service
vpn-tun      ← vpn-core, vpn-service
vpn-proto    ← vpn-core
vpn-core     ← vpn-service, vpn-ipc
vpn-ipc      ← vpn-service, vpn-desktop
```

Разрешённые направления (стрелка = «может зависеть от»):

| Крейт | Может зависеть от | Не может |
|---|---|---|
| `vpn-config` | serde, url, base64, uuid, thiserror | ничего из проекта |
| `vpn-routing` | serde, ipnet, thiserror | vpn-proto, vpn-tun, vpn-core |
| `vpn-dns` | serde, thiserror | vpn-routing, vpn-proto |
| `vpn-tun` | thiserror, async-trait | vpn-proto, vpn-routing |
| `vpn-proto` | vpn-config, tokio, async-trait | vpn-routing, vpn-tun, vpn-core |
| `vpn-core` | vpn-config, vpn-proto, vpn-routing | vpn-tun, vpn-dns, vpn-ipc |
| `vpn-ipc` | vpn-config, vpn-core, serde | vpn-tun, vpn-proto |
| `vpn-service` | все библиотечные крейты | — |
| `vpn-desktop` | vpn-ipc | vpn-tun, vpn-proto |

Циклы запрещены. Если появляется потребность в обратной зависимости —
это сигнал к выделению нового крейта или трейта, а не к нарушению правила.

## 4. Поток данных

Подключение:

1. UI отправляет `Request::Connect { profile, preset }`.
2. Служба валидирует запрос, выбирает outbound (`vpn-proto`), строит `RoutingEngine`.
3. `vpn-tun` создаёт интерфейс, назначает адрес, поднимает маршруты и DNS.
4. Пакеты из TUN попадают в userspace-стек, оттуда — в `vpn-core`.
5. `vpn-core` спрашивает `vpn-routing` о решении для каждого соединения.
6. `direct` → системный выход, `proxy` → `Outbound::dial_*`, `block` → отклонение.
7. Статистика агрегируется и по запросу отдаётся в UI.

Отключение выполняется в обратном порядке; маршруты и DNS восстанавливаются
**даже при ошибке** (guard-объекты, `Drop` не должен быть единственной защитой).

## 5. Рантайм и конкурентность

- Один `tokio` multi-thread рантайм на службу.
- Блокирующие операции — только через `spawn_blocking`.
- Никаких `std::thread::sleep` в async-коде.
- Все сетевые операции имеют таймаут; бесконечных ожиданий нет.
- Общие состояния — `Arc<...>` + `RwLock`/каналы; без глобальных мутабельных статиков.
- Отмена (cancellation) должна быть безопасной: ресурсы освобождаются детерминированно.

## 6. Windows-специфика

| Задача | Механизм |
|---|---|
| TUN | `wintun.dll` (динамическая загрузка, проверка подписи DLL) |
| Маршруты | `CreateIpForwardEntry2` / `iphlpapi` |
| Kill switch | WFP-фильтры (`windows` crate) |
| Маппинг сокет → PID | `GetExtendedTcpTable` / `GetExtendedUdpTable` |
| Служба | SCM, `ServiceMain`, restart при падении |
| Секреты | DPAPI (per-machine + per-user scope) |

Весь платформенный код изолируется в `vpn-tun`/`vpn-core` под `#[cfg(windows)]`.
Остальные крейты не должны знать про Windows API.

## 7. Расширяемость

- **Новый протокол** — реализация `Outbound` в `vpn-proto`, без изменений в ядре.
- **Новый матчер** — расширение `Matcher` в `vpn-routing` + версия схемы пресетов.
- **Новый транспорт** (WS, gRPC, XHTTP) — внутри протокола, не в ядре.
- **Новая платформа** — отдельный крейт `vpn-tun-<os>` и адаптер IPC.

## 8. Что требует ADR

- изменение границ крейтов или появление нового;
- смена модели привилегий;
- новый протокол с нестандартной лицензией;
- изменение формата пресетов/конфигов;
- добавление зависимости, влияющей на безопасность (крипто, сеть, FFI).
