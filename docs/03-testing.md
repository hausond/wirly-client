# Стратегия тестирования

Статус: **действует**. Политика покрытия — блокирующая.

## 1. Главное правило

> **100% покрытия строк в `crates/**` — с первого дня.**

Не «когда-нибудь», не «после релиза». Если код нельзя покрыть тестом —
значит, он спроектирован неправильно (см. §6 «Исключения»).

Дополнительно:

- **patch coverage = 100%**: каждая добавленная/изменённая строка покрыта;
- **branch coverage ≥ 90%** для `vpn-routing` (растёт до 100% к фазе 2);
- бинарники (`apps/*`) исключены из подсчёта строк, но обязаны иметь
  интеграционные тесты на критичные сценарии.

## 2. Пирамида

| Уровень | Доля | Что проверяет | Скорость |
|---|---|---|---|
| Unit | ~75% | чистые функции, парсеры, правила, состояния | мс |
| Integration | ~20% | крейт + локальные фейки (TCP/UDP loopback, in-memory IPC) | секунды |
| E2E | ~5% | реальный сервер, реальный TUN, ручной/ночной прогон | минуты |

Требования:

- Unit-тесты **не ходят в сеть, не спят, не читают реальное время**.
- Время, случайность, DNS — через инъекцию (`Clock`, `Rng`, trait-резолвер).
- E2E-тесты не входят в обязательный PR-гейт, но входят в ночной прогон.

## 3. Где лежат тесты

- Unit — рядом с кодом, `#[cfg(test)] mod tests`.
- Integration — `crates/<crate>/tests/*.rs`.
- E2E — `tests/e2e/*` (отдельный workspace-крейт или скрипты), помечаются
  `#[ignore]` и запускаются отдельной командой.

## 4. Именование и структура

```rust
#[test]
fn given_udp_rule_when_connection_is_udp_then_blocked() { ... }
```

- Один тест — одна причина падения.
- Ассерты — конкретные (`assert_eq!`), а не `assert!(result.is_ok())`, если важна причина.
- Тестовые данные — фабрики (`fn profile() -> Profile`), без дублирования «магии».
- Тест не должен зависеть от порядка выполнения других тестов.

## 5. Обязательные тесты на изменение

| Тип изменения | Минимум |
|---|---|
| Багфикс | регрессионный тест, воспроизводящий баг |
| Новая функция | unit + граничные случаи + ошибка |
| Парсер внешнего формата | валидные, невалидные, граничные, fuzz-цель |
| Новое правило роутинга | таблица истинности + приоритет |
| Новый протокол | golden vectors + interop против эталонного сервера |
| Изменение публичного API | doc-пример + semver-проверка |
| Работа с ФС/сетью | тест на ошибку ввода-вывода |

## 6. Исключения из покрытия

Допустимы **только** для:

1. платформенного FFI (`#[cfg(windows)]` обёртки wintun/WFP), если
   соответствующий safe-API покрыт интеграционным тестом;
2. `fn main()` бинарников;
3. сгенерированного кода (bindings), помеченного `// @generated`.

Оформление: модуль помечается `#[coverage(off)]` (когда стабилизируется) либо
исключается в конфиге `llvm-cov`; причина фиксируется в `docs/adr`.

Запрещено исключать «сложный» или «неудобный» код.

## 7. Специальные виды тестов

- **Property-based** (`proptest`): инварианты правил роутинга, fake-IP пула,
  парсеров подписок.
- **Fuzzing** (`cargo-fuzz`): парсеры share-ссылок, Clash/sing-box JSON,
  бинарные rule-set'ы. Цель фаззинга обязана быть в CI (smoke, 60 с) и в ночном прогоне.
- **Mutation testing** (`cargo-mutants`): ежемесячно для `vpn-routing`,
  `vpn-config`, `vpn-dns`. Порог: ≥ 90% выживших мутантов убито.
- **Golden vectors**: для протоколов — зафиксированные байтовые последовательности
  (handshake, заголовки), проверяемые без сети.

## 8. Детерминизм и стабильность

- Запрещены `sleep` в тестах; ожидание — через каналы/условия с таймаутом.
- Запрещены тесты, зависящие от внешнего DNS/интернета в unit/integration.
- Параллелизм: тесты должны проходить при `--test-threads=16`.
- Плавающий тест (flaky) — инцидент. Правило: в течение 24 часов либо
  исправить, либо удалить с issue на восстановление. Повторные прогоны для
  «позеленения» запрещены.

## 9. Команды

```powershell
cargo test --workspace
cargo llvm-cov --workspace --exclude vpn-service --exclude vpn-desktop `
  --fail-under-lines 100
cargo llvm-cov --workspace --exclude vpn-service --exclude vpn-desktop `
  --html --output-dir target/coverage
cargo mutants -p vpn-routing -p vpn-config -p vpn-dns
cargo fuzz run parse_share_link -- -max_total_time=60
```

## 10. CI-гейт покрытия

- Шаг `coverage` обязателен и блокирующий.
- Порог: `--fail-under-lines 100` для библиотечных крейтов.
- Падение покрытия на 0.01% = красный CI.
- Отчёт (`lcov`/HTML) публикуется артефактом PR.

> Локально на `stable-x86_64-pc-windows-gnu` инструментация покрытия недоступна
> (`can't find crate for profiler_builtins`). Это ограничение тулчейна, а не
> разрешение не покрывать код: обязательный гейт выполняется в CI на MSVC,
> а `scripts/check.ps1` помечает локальный coverage как `SKIP`.
> Если нужен локальный отчёт — используйте MSVC-тулчейн.

## 11. Тестовая документация

- Каждый протокол в `docs/08-protocols.md` имеет раздел «Как тестируется».
- Каждое правило роутинга — строку в тестовой матрице `docs/07-routing-spec.md`.
- Новые тестовые сценарии E2E описываются в PR, а не только в коде.

## 12. Антипаттерны (запрещены)

- `#[ignore]` без issue и срока.
- Тест без ассертов.
- Мок, возвращающий захардкоженный успех для проверки успеха.
- «Тест на компиляцию» вместо проверки поведения.
- Отключение теста ради прохождения CI.
- `assert!(true)`.
