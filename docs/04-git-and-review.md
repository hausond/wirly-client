# Git, ветки и ревью

Статус: **действует**. Нарушение процесса = откат изменений.

## 1. Модель ветвления

- Trunk-based development. Долгоживущих веток нет.
- `main` — всегда релизопригодна.
- Ветка живёт **≤ 3 рабочих дней**; иначе дробится.

Именование веток:

```
feat/<scope>-<short-desc>
fix/<scope>-<short-desc>
refactor/<scope>-<short-desc>
test/<scope>-<short-desc>
docs/<scope>-<short-desc>
chore/<short-desc>
```

Примеры: `feat/routing-process-matcher`, `fix/config-base64-padding`,
`docs/agent-playbook`.

## 2. Защита `main`

Включено на уровне GitHub (обязательно к настройке):

- прямые пуши запрещены (включая администраторов);
- force-push и удаление ветки запрещены;
- требуется PR;
- обязательные проверки: `fmt`, `clippy`, `test`, `coverage`, `deny`, `audit`, `docs`;
- обязательное разрешение всех обсуждений;
- линейная история (squash merge);
- 1 approval для обычных изменений, 2 — для `vpn-proto/**`, `vpn-tun/**`,
  `docs/09-security.md`, `.github/**`.

## 3. Коммиты

Формат Conventional Commits:

```
<type>(<scope>): <imperative summary>

<body: почему, а не что>

Refs: #123
```

Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`, `revert`.

Требования:

- заголовок ≤ 72 символов, в повелительном наклонении, без точки;
- один коммит = одно логическое изменение;
- запрещены коммиты «wip», «fix», «asdf»;
- запрещено смешивать форматирование и логику в одном коммите.

## 4. Pull Request

Обязательные элементы описания (см. шаблон):

1. **Что** и **зачем**.
2. **Как проверял** (команды, ручные сценарии).
3. **Риски** и влияние на безопасность.
4. **Документация** — какие доки обновлены.
5. **Скриншоты/логи** для UI/поведения.
6. Ссылка на issue.

Ограничения:

- ≤ 400 изменённых строк (без тестов и сгенерированного кода);
- если больше — дробить;
- запрещены «мусорные» диффы (переформатирование чужих файлов, случайные правки).

## 5. Ревью

Ревьюер обязан проверить:

- [ ] соответствие уставу и архитектуре;
- [ ] нет нарушения границ крейтов;
- [ ] тесты покрывают новое поведение и граничные случаи;
- [ ] ошибки не глотаются, нет `unwrap` вне тестов;
- [ ] нет секретов и приватных данных в коде/логах;
- [ ] обновлена документация;
- [ ] нет `#[allow]` без `WHY:`;
- [ ] нет новых зависимостей без обоснования и проверки лицензии;
- [ ] публичный API документирован.

Правила общения:

- комментарий = вопрос или конкретное требование, без вкусовщины;
- «nit:» — не блокирует merge, но фиксируется;
- автор отвечает на каждый комментарий (resolve или аргумент);
- LGTM ставится только после зелёного CI.

## 6. Merge

- Только squash merge.
- Заголовок squash-коммита = заголовок PR (Conventional Commit).
- Ветка удаляется после merge.
- Merge в `main` запускает сборку артефактов (nightly-канал).

## 7. Hotfix

Разрешён только при инциденте (утечка, краш, блокирующий баг):

1. ветка `hotfix/<incident-id>`;
2. минимальный дифф + тест;
3. ревью security/техлида;
4. после merge — post-mortem в `docs/incidents/` в течение 48 часов.

## 8. Теги и версии

- `vMAJOR.MINOR.PATCH` (semver).
- Тег ставится только на `main` после релизного чек-листа.
- Артефакты подписываются; хеши публикуются в релизе.

## 9. Запрещено

- `git push --force` в любую общую ветку;
- merge-коммиты в `main`;
- правка CI ради «позеленения»;
- отключение/удаление тестов без issue;
- коммит секретов (даже временно) — немедленная ротация ключа;
- прямые пуши в `main`.
