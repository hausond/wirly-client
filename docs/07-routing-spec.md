# Спецификация роутинга и пресетов

Статус: **действует**. Изменение семантики = breaking change + ADR.

## 1. Модель

```
Preset { name, description, default_action, rules[] }
Rule   { match: Matcher, action: Action, note? }
```

Решение принимается **первым совпавшим правилом**. Если ни одно не совпало —
применяется `default_action`.

## 2. Схема JSON

### Preset

```json
{
  "schema_version": 1,
  "name": "Bypass RU",
  "description": "RU-сайты напрямую, остальное через туннель",
  "default_action": { "proxy": "default" },
  "rules": []
}
```

| Поле | Тип | Обязательно | Примечание |
|---|---|---|---|
| `schema_version` | integer | да (с v0.2) | несовпадение = отказ загрузки |
| `name` | string | да | уникален в рамках профиля |
| `description` | string | нет | человекочитаемое |
| `default_action` | Action | да | применяется при отсутствии совпадений |
| `rules` | Rule[] | да | порядок важен |

### Rule

```json
{
  "match": { "type": "domain", "value": "youtube.com", "mode": "suffix" },
  "action": { "proxy": "default" },
  "note": "видео"
}
```

### Matcher

| `type` | Поля | Семантика |
|---|---|---|
| `domain` | `value`, `mode` (`exact`/`suffix`/`keyword`) | сравнение домена после нормализации |
| `ip` | `cidr` | вхождение IP в подсеть |
| `port` | `value` | точное совпадение порта |
| `process` | `name` | имя исполняемого файла (Windows), без пути |
| `network` | `value` (`tcp`/`udp`) | транспорт |
| `any` | — | всегда истинно |

### Action

| Значение | Смысл |
|---|---|
| `"direct"` | выпустить напрямую |
| `"block"` | отклонить соединение |
| `{ "proxy": "<name>" }` | отправить в указанный outbound |

## 3. Нормализация

- Домен приводится к нижнему регистру, обрезается завершающая точка.
- `suffix`: совпадение `a.b` и любого `*.a.b`, но **не** `nota.b`.
- `keyword`: подстрока; применять осторожно (широкие правила).
- `exact`: строгое равенство.
- IDN: домены сравниваются в punycode (`xn--...`); преобразование — на входе.
- CIDR: IPv4 и IPv6 раздельно; IPv4-mapped IPv6 приводится к IPv4.

## 4. Приоритеты и порядок

1. Правила оцениваются сверху вниз; первое совпадение выигрывает.
2. Более специфичные правила автор ставит выше общих.
3. `default_action` — последняя инстанция, не правило.
4. Порядок правил — часть контракта пресета; менять его в минорной версии нельзя.

## 5. Сниффинг и fake-IP

- `ConnectionInfo.domain` заполняется из TLS SNI / HTTP Host / QUIC SNI.
- Если домен известен из fake-IP, приоритет у fake-IP-мэппинга.
- Если домен неизвестен, доменные правила не срабатывают — работает IP-правило
  или `default_action`.
- Сниффинг не должен задерживать первый пакет дольше 50 мс.

## 6. Process matching (Windows)

- Имя процесса берётся из маппинга сокет → PID (`GetExtendedTcpTable`/`UdpTable`).
- Сравнение — регистронезависимое, только basename (`Wow.exe`, не полный путь).
- Если процесс определить не удалось, правило не срабатывает (fail-open к
  следующему правилу, но **не** к `direct`).
- Кэш маппинга: ≤ 1 с, инвалидация при закрытии сокета.
- Ограничение документируется в UI: «по процессу» не работает для системных служб.

## 7. Пресеты: правила авторинга

Обязательные пресеты v1:

| Имя | Назначение |
|---|---|
| `Global` | всё в туннель, кроме LAN |
| `Bypass RU` | RU-домены/игры напрямую |
| `Gaming` | процессы игр и лаунчеров напрямую |
| `Work/AI` | только выбранные сервисы в туннель |

Требования:

- приватные диапазоны (`10/8`, `172.16/12`, `192.168/16`, `127/8`, `169.254/16`)
  всегда `direct` — это инвариант, проверяется тестом;
- никаких `any: direct` в пресетах, где по умолчанию прокси;
- каждый пресет имеет тестовую матрицу (см. §9);
- имя пресета стабильно (используется в профилях).

## 8. Версионирование

- `schema_version` увеличивается при любом breaking change.
- Старые версии читаются минимум одну мажорную версию клиента (миграция).
- Неизвестные поля в пресете → ошибка загрузки (строгий режим).
- Пресеты пользователя не перезаписываются при обновлении; миграция — копией.

## 9. Тестовая матрица (обязательная)

Для каждого пресета проверяется:

- LAN-адрес → `direct`;
- домен из правила → ожидаемое действие;
- похожий домен (`notyoutube.com`) → **не** совпадает;
- неизвестный домен → `default_action`;
- UDP-правило (если есть) → ожидаемое действие;
- процесс из правила → ожидаемое действие;
- порядок правил: более специфичное выше — выигрывает.

## 10. Ошибки

| Ситуация | Поведение |
|---|---|
| невалидный CIDR | пресет не загружается, ошибка с указанием правила |
| неизвестный `type` | ошибка загрузки |
| `proxy` указывает на несуществующий outbound | ошибка при подключении, не при загрузке |
| пустой `rules` | допустимо, работает `default_action` |

## 11. Пример: «игра напрямую, остальное в туннель»

```json
{
  "schema_version": 1,
  "name": "Gaming",
  "default_action": { "proxy": "default" },
  "rules": [
    { "match": { "type": "ip", "cidr": "10.0.0.0/8" }, "action": "direct" },
    { "match": { "type": "port", "value": 3724 }, "action": "direct" },
    { "match": { "type": "process", "name": "Wow.exe" }, "action": "direct" }
  ]
}
```

Порядок здесь не случаен: LAN → порт → процесс. Любое изменение порядка
требует обновления тестовой матрицы.
